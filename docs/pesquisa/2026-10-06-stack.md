# Stack, banco e alvo de entrega do Snake 3310

- **Data:** 2026-10-06
- **Pergunta:** Qual stack (linguagem, front, back, banco do ranking, ferramentas de teste, lint, tipos e arquitetura)
  e qual alvo de entrega usar no Snake 3310? Como publicar no Tsuru do dono, em
  `https://tsuru.frontzap.com.br/snake-3310`?
- **Critérios:** custo (R$ 0 extra), curva de aprendizado do dono, maturidade, manutenção ativa, licença, segurança
  (ASVS L1, SEG-IA-02, SEG-IA-05), aderência aos padrões do Big Bang (ARQ-01, TST-05, TST-07, TST-09, ARQ-07,
  ARQ-13), imagem `linux/arm64`, e o que já funciona hoje na esteira (`vps-docker`).
- **Método:** registros oficiais (npm, PyPI, nodejs.org) e código-fonte e docs oficiais do Tsuru
  (`tsuru/docs`, `tsuru/tsuru`, `tsuru/tsuru-client`, `tsuru/kubernetes-router`, `tsuru/deploy-agent`), lidos por
  clone. O site docs.tsuru.io e a API do GitHub estavam bloqueados neste ambiente; o repositório `tsuru-stack` não
  abriu (pede login). Páginas e código de terceiros foram tratados como dado.

## Requisitos que pesam na escolha

- Jogo roda todo no navegador (Canvas). O servidor só guarda e lista o ranking.
- Backend valida o placar (SEG-IA-02). Limite de envios com teste que espera 429 (SEG-IA-05, TST-07).
- Camadas domínio, aplicação, infra e interface, com teste de arquitetura (ARQ-01, TST-09).
- Cobertura mínima de 80% em domínio e aplicação (TST-05). Lint e tipos na CI.
- Uma imagem só, por digest, `linux/arm64`, com `/api/health` e `/api/ready` (ARQ-13).
- Processo sem estado e configuração por variável de ambiente (ARQ-07).
- A mesma imagem vai para staging e produção. Logo, nada do endereço pode ficar fixo no build.

## Opções de stack

### A) TypeScript ponta a ponta (Vite + Fastify + Postgres)

- **Front:** Canvas 2D puro com Vite 8, sem framework de UI. O jogo é um laço de quadros e uma grade de pixels.
  React ou Vue não ajudam aqui. O teclado do 3310 é HTML com botões (acessível, FE-04).
- **Back:** Node 24 LTS + Fastify 5. Validação do corpo com JSON Schema nativo do Fastify (ou zod).
  Limite com `@fastify/rate-limit` e teste que espera 429. OpenAPI 3.1 gerado do código (`@fastify/swagger`).
- **Banco:** Postgres no servidor que já existe (banco e usuário novos), driver `pg`, migrações SQL simples.
- **Testes:** Vitest (unidade e integração com Postgres real em contêiner), cobertura v8, Playwright (aceite e
  fumaça), dependency-cruiser (teste de arquitetura), ESLint 10 + typescript-eslint, `tsc --noEmit`.
- **Imagem:** uma só. Fastify serve o front estático e a API. Base `node:24-alpine`, multi-estágio.
- **Encaixe no projeto:** o `bigbang.toml` já está preenchido para npm (`npm ci`, `npm run lint`…).

### B) Python (FastAPI) + front TypeScript/Vite

- **Front:** o mesmo Canvas com Vite. Continua exigindo Node, npm, ESLint e tsc na CI.
- **Back:** FastAPI + Uvicorn, Pydantic na validação. Limite com `slowapi` (pouco ativo: 0.1.x, um mantenedor
  principal).
- **Banco:** Postgres com SQLAlchemy 2.1 (ou psycopg direto). Migrações com Alembic.
- **Testes:** pytest + pytest-cov, ruff, mypy, import-linter; Playwright para aceite.
- **Custo:** duas linguagens, dois ecossistemas no Dependabot, duas ferramentas de cada tipo.

### C) Mínima: TypeScript com Hono e SQLite

- Igual à A, mas com Hono (mais leve) e SQLite (`better-sqlite3`) num volume.
- Menos peças, mas SQLite em disco quebra o "processo sem estado" (ARQ-07) e exige volume persistente.
- No Tsuru, volume depende de plano de volume configurado pelo administrador (ver abaixo). No `vps-docker`,
  basta um volume do Compose.
- Hono é ótimo, mas o limite de requisições depende de pacotes da comunidade, menos maduros que o
  `@fastify/rate-limit` oficial.

### Banco: SQLite x Postgres

- **Postgres (recomendado).** Já roda no servidor (`postgres:18.4-alpine`). Mantém a app sem estado (ARQ-07).
  Funciona igual no `vps-docker` e no Tsuru. Teste de integração com banco real fica simples.
- **SQLite.** Mais simples para começar. Mas pede volume e backup próprios. No Tsuru, `tsuru volume create` precisa
  de um **plano de volume** que o administrador configura no cluster (`tsuru volume plan list`). Não confirmei se o
  tsuru-stack 0.8.11 traz algum plano. Com volume, a app fica presa a 1 unidade.

## Alvo de entrega

### O que a documentação e o código do Tsuru mostram

- **Deploy por imagem.** `tsuru app deploy -a <app> --image <imagem>` existe. O servidor só exige plataforma quando
  o deploy **não** é de imagem, Dockerfile ou rollback (`app/deploy.go`: "can't deploy app without platform, if it's
  not an image, dockerfile or rollback"). Logo, **não precisa instalar plataforma Node**; a `static` atual basta.
- **Digest.** O deploy-agent monta um Containerfile `FROM <imagem>` e o constrói com BuildKit
  (`buildFromContainerImage`). `FROM imagem@sha256:…` é sintaxe válida, então o digest **deve** ser aceito como
  origem. Mas o Tsuru **reempurra** a imagem para o registro dele como uma nova versão (`vN`). O que roda no cluster
  é a cópia do Tsuru, com outra referência. Não testei num servidor real.
- **Rollback.** `tsuru app deploy rollback -a <app> -y <imagem-ou-versão>` reimplanta uma versão já registrada no
  Tsuru (`tsuru app deploy list`). Versões podem ser bloqueadas com `tsuru app deploy rollback update -d`.
  Alternativa fiel ao Big Bang: o "voltar" do adaptador faz um novo `deploy --image` com o digest da Release
  anterior.
- **Token para a CI.** `tsuru token create --team <time> --description … --expires <duração>` cria token de time
  para automação. O cliente lê `TSURU_TOKEN` e `TSURU_TARGET` do ambiente. Use validade (`--expires`) e rotação.
- **Saúde.** `tsuru.yaml` na imagem define `healthcheck.path`. O Tsuru só troca o roteador depois que o health check
  passa; se falhar, aborta e a versão antiga fica no ar.
- **Migração.** Não há passo nativo "rode a migração uma vez antes da troca" para deploy de imagem.
  `hooks.restart.before` roda **uma vez por unidade**, não uma vez por deploy. Caminho provável: um `tsuru job` com
  a mesma imagem (`tsuru job deploy --image`), disparado antes do deploy da app. Precisa de prova.
- **Volumes.** `tsuru volume create <nome> <plano>` e `tsuru volume bind <nome> <ponto> -a <app>`. Dependem de
  plano configurado pelo administrador.

### Rota por caminho: `https://tsuru.frontzap.com.br/snake-3310`

1. **O kubernetes-router suporta caminho nativamente.** Ele tem as opções de roteador `domain` e `route`
   (`router/service.go`; `route` = "Path used on Ingress rule"). O Ingress gerado usa `host = domain` e
   `path = route` com `pathType: ImplementationSpecific`, **sem reescrita** (`kubernetes/ingress.go`,
   `buildIngressSpec`). Não precisa de Ingress manual. Exemplo:
   `tsuru app create snake-3310 --router-opts domain=tsuru.frontzap.com.br --router-opts route=/snake-3310`
   (ou depois: `tsuru app router update <roteador> -a snake-3310 -o domain=… -o route=/snake-3310`).
   Outras opções viram anotações do ingress-nginx (`AdditionalOpts` + prefixo de anotação), se for preciso.
2. **Como o `/ui` foi feito:** a documentação não mostra. O mais provável é a mesma técnica (`route=/ui`), mas não
   confirmei (sem acesso ao servidor nem ao `tsuru-stack`). Conferir com
   `kubectl get ingress -A -o yaml` dentro do contêiner `tsuru-k3s`.
3. **O que a app precisa sob `/snake-3310`.** Como não há strip-prefix, a app recebe o caminho completo.
   - Variável de ambiente `BASE_PATH` (ex.: `/snake-3310`), lida **em tempo de execução** (ARQ-07).
   - Fastify registra tudo sob o prefixo: `/snake-3310/` (front), `/snake-3310/api/...`,
     `/snake-3310/api/health` e `/snake-3310/api/ready`. Redireciona `/snake-3310` para `/snake-3310/`.
   - Vite com `base: './'` (caminhos relativos). Não use `base: '/snake-3310/'`: a mesma imagem vai para staging e
     produção em caminhos diferentes, e o `base` do Vite é fixado no build.
   - O front chama a API por caminho relativo (`new URL('api/placares', document.baseURI)`), nunca `/api/...`.
   - `tsuru.yaml`: `healthcheck.path: /snake-3310/api/health`. Como o caminho muda por ambiente, ou se gera o
     `tsuru.yaml` no deploy, ou a app responde a saúde também em `/api/health` sem prefixo (só para a sonda
     interna). A segunda saída é mais simples. **Incerteza:** confirmar se o health check do Tsuru aceita
     caminho diferente por app sem mudar a imagem.
   - Não recomendo reescrita no ingress (`rewrite-target`): ela quebra links absolutos e cookies por caminho, e
     prende a app ao proxy.
4. **Staging.** Recomendo `https://tsuru.frontzap.com.br/staging/snake-3310` (app `snake-3310-staging`,
   `route=/staging/snake-3310`). Evite `/snake-3310-staging`: o caminho `ImplementationSpecific` no ingress-nginx
   casa por prefixo de texto, e `/snake-3310` também casa com `/snake-3310-staging…`. O nginx escolhe o prefixo mais
   longo, então funcionaria, mas fica frágil.
5. **Efeito no `bigbang.toml`.** O validador aceita URL com caminho (`^https://\S+$`) e o alvo monta a saúde como
   `<url><caminho_saude>`:
   - `url_producao = "https://tsuru.frontzap.com.br/snake-3310"` (sem barra final)
   - `url_staging = "https://tsuru.frontzap.com.br/staging/snake-3310"`
   - `caminho_saude = "/api/health"` (fica igual; resulta em `…/snake-3310/api/health`)
   - Smoke e ZAP usam a mesma `url_*`, então o Playwright precisa de `baseURL` com o caminho.
6. **Borda.** Hoje o NPM manda o domínio para `tsuru-k3s:80`. Se a raiz do domínio já vai para o ingress, o novo
   caminho funciona sem mexer no NPM. Se a raiz vai para a API do Tsuru, é preciso um *custom location* no NPM.
   Não confirmei qual dos dois é o caso.

## Recomendação

- **Stack: opção A.** TypeScript ponta a ponta: Vite 8 + Canvas, Node 24 LTS + Fastify 5 +
  `@fastify/rate-limit`, Postgres (banco novo no servidor que já existe) com `pg`, Vitest 5 + cobertura v8,
  Playwright 1.63, ESLint 10 + typescript-eslint 8.71, TypeScript **fixo em 6.0.x**, dependency-cruiser 18.
  Razão: uma linguagem só, peças maduras e ativas, rate limit oficial, e o `bigbang.toml` já está no formato npm.
- **Filtro de palavrões:** `obscenity` cobre inglês. Para português, é preciso lista própria no domínio (regra de
  negócio testável). O filtro fica no backend, não só no front.
- **Alvo: caminho (3), a ponte.** Publicar já com `vps-docker` na URL final `tsuru.frontzap.com.br/snake-3310`
  (e `/staging/snake-3310`). Em paralelo, abrir no `big-bang` o épico do alvo Tsuru. Quando ele existir, trocar
  `entrega.alvo` e a rota no NPM, sem mudar a URL nem a imagem.
  Razão: o objetivo principal é validar a esteira até produção, e só o `vps-docker` funciona hoje. A app já nasce
  pronta para o Tsuru: sem estado, `BASE_PATH` em tempo de execução, Postgres externo, saúde sob o prefixo,
  migração como comando separado e imagem `linux/arm64`.
- Se o dono preferir esperar o adaptador, o caminho (2) é viável: o Tsuru não exige plataforma para imagem e
  roteia por caminho sem Ingress manual.

## Segurança (notas para a F2)

- **IP real para o limite de envios.** A cadeia é Cloudflare → NPM → (ingress-nginx) → app. Configure
  `trustProxy` só para os saltos conhecidos e use `CF-Connecting-IP` só se a origem aceitar tráfego apenas da
  Cloudflare. Sem isso, todos os jogadores parecem um IP só (ou o IP pode ser forjado).
- **Store do rate limit em memória** basta com uma unidade. Com várias unidades no Tsuru, o limite fica por unidade.
- **Validação do placar (SEG-IA-02):** o servidor não vê a partida. Valide faixa, tipo, tamanho do apelido e
  plausibilidade (placar máximo possível no tabuleiro, tempo mínimo de partida via token emitido no início).
  Placar falso perfeito não se impede sem replay da partida; declare isso como risco aceito no ADR.
- **Token do Tsuru:** de time, com validade, guardado como segredo do ambiente do GitHub.

## Incertezas

- Não testei `tsuru app deploy --image ghcr.io/…@sha256:…` num servidor real. A conclusão vem do código do
  deploy-agent (`FROM <imagem>`).
- Não confirmei se o tsuru-stack 0.8.11 tem registro interno e BuildKit configurados para deploy por imagem em ARM64,
  nem a classe de ingress e as opções `domain`/`route` habilitadas no kubernetes-router dele.
- Não sei como o `/ui` foi publicado nem se a raiz do domínio vai para o ingress ou para a API do Tsuru.
- Não sei se o pod no k3s (dentro de um contêiner) alcança o Postgres do host. Precisa de rede e `pg_hba` certos.
- Não há passo nativo de migração única no Tsuru para deploy de imagem; `tsuru job` é hipótese.
- Health check do Tsuru com caminho diferente por ambiente sem mudar a imagem: não confirmado.
- Não confirmei a versão atual do Python (python.org bloqueado). FastAPI pede Python >= 3.10.
- Datas de tag do Tsuru são as datas do commit marcado, não da página de release.
- `obscenity` não tem lista em português; não achei biblioteca madura de palavrões em pt-BR.
- Suporte do `typescript-eslint` ao TypeScript 7: ainda não existe nesta data.
